## The approved design (already decided by the user — implement it, do not re-derive it)

New client component `components/site-nav.tsx`, default-exported as `SiteNav`, taking a single prop
`role: "patient" | "doctor" | "admin" | null`.

A module-scope constant `NAV_LINKS`, typed
`Record<"patient" | "doctor" | "admin", { href: string; labelKey: TranslationKey }[]>`:

| role | links, in order |
|------|-----------------|
| patient | `/patient` -> `nav.dashboard`, `/search` -> `nav.search`, `/patient/appointments` -> `nav.appointments`, `/patient/favorites` -> `nav.favorites` |
| doctor | `/doctor` -> `nav.dashboard`, `/doctor/appointments` -> `nav.appointments`, `/doctor/schedule` -> `nav.schedule` |
| admin | `/admin` -> `nav.dashboard`, `/admin/appointments` -> `nav.appointments`, `/admin/doctors` -> `nav.doctors`, `/admin/locations` -> `nav.locations`, `/admin/specialties` -> `nav.specialties`, `/admin/users` -> `nav.users` |

A second module-scope constant `ANON_LINKS` holding the single entry `/search` -> `nav.search`.
`const links = role ? NAV_LINKS[role] : ANON_LINKS;`

The component returns a fragment holding two things:

1. A `<nav aria-label={t("nav.aria_label")}>` carrying the Tailwind classes `hidden items-center gap-4 sm:flex`,
   mapping `links` to `next/link` `<Link>` elements. Each link sets
   `aria-current={pathname === href ? "page" : undefined}` and swaps its className between an active variant
   (`text-sm font-semibold`) and an inactive one (`text-sm text-muted-foreground hover:text-foreground`).
2. A `<Popover open={open} onOpenChange={setOpen}>` whose `PopoverTrigger` uses
   `render={<Button variant="ghost" size="icon" className="size-11 sm:hidden" aria-label={t("nav.menu_label")} />}`
   and whose child is the lucide `<Menu />` icon; its `<PopoverContent align="end" className="w-56">` holds a
   `<nav data-testid="site-nav-menu" className="flex flex-col gap-1">` mapping the SAME `links` array to
   `<Link>` elements that additionally call `setOpen(false)` on click and carry the same `aria-current` logic.

State: `const [open, setOpen] = useState(false)`. Hooks: `useT()` from `@/lib/i18n/locale-provider`,
`usePathname()` from `next/navigation`. Icon: `import { Menu } from "lucide-react"` — the same named-import
style `components/notification-bell.tsx:3` uses for `Bell`. `Menu` is exported by the installed
`lucide-react@^1.28.0` (verified).

**Wiring in `components/site-header.tsx`:** wrap the existing logo `<Link href="/">` and the new `<SiteNav />`
in a single `<div className="flex items-center gap-4">` placed where the logo is today, leaving the existing
`justify-between` header and the existing right-hand controls div (language switcher, name, bell, logout)
exactly as they are. Pass the role via a narrowing constant computed in the header, NOT `profile?.role ?? null`
directly — see "Why the role prop needs an explicit narrowing" below.

## Why the role prop needs an explicit narrowing

`lib/supabase/server.ts`'s `createServerClient()` is called with no `Database` generic and there is no
generated types module in `lib/supabase/`, so `profile` in `components/site-header.tsx` is effectively `any`.
Passing `profile?.role ?? null` would therefore typecheck by accident rather than by proof, and would forward
any stray string straight into `NAV_LINKS[role]` — producing `undefined` and a runtime crash on `.map()`.

Compute an explicitly narrowed constant in the header instead: check `profile?.role` against the three literals
and fall back to `null`. That makes "unknown or missing role" behave exactly like an anonymous visitor (the
Search-only list), which is the same fail-closed posture `app/page.tsx` already takes for an unrecognized role.

## The physical-direction utility set (RTL invariant — plan 06-10)

Plan 06-10 proved, by repo-wide grep, that `app/` and `components/` (excluding `components/ui/`) contain zero
physical-direction Tailwind utilities: no `pl-`/`pr-`/`ml-`/`mr-` numeric variants, no `text-left`/`text-right`,
no numeric `left-`/`right-` inset utilities, and no `flex-row-reverse`. This invariant has held for five phases
and is re-asserted as a gate in Task 2. Use logical equivalents only (`ps-`/`pe-`/`ms-`/`me-`/`start-`/`end-`,
`text-start`/`text-end`) and `align="end"` on the popover — and do not name any of the forbidden utilities in a
source comment, or the gate greps its own explanation and fails.

The design as specified needs none of them: `gap-4`, `gap-1`, `px-2`, `py-1.5`, `w-56`, `size-11` are all
direction-neutral. `align="end"` is Base UI's logical alignment and already mirrors correctly in RTL — the same
value `NotificationBell` uses (`components/notification-bell.tsx:197`). Base UI's `Positioner` applies collision
shifting, so an `align="end"` popup anchored to a trigger near the inline-start edge stays on screen.

## The Playwright substring trap (this WILL bite if ignored)

`getByRole(role, { name })` matches the accessible name as a case-insensitive **substring** unless
`exact: true`. Real collisions that exist today:

| nav label | also a substring of |
|-----------|---------------------|
| `Appointments` | `My appointments` (patient + doctor appointment page titles, dashboard links) |
| `Search` | `Search doctors` (patient dashboard link), `Back to search` (doctor profile) |
| `Favorites` | `My favorites` (patient dashboard link + favorites page title) |
| `Schedule` | `My schedule`, `Manage my schedule` (doctor dashboard link) |
| `Dashboard` | `My dashboard`, `Admin dashboard` (page headings) |

Every nav assertion must therefore be scoped AND exact:
- desktop: `page.getByRole("navigation", { name: "Main navigation" }).getByRole("link", { name: X, exact: true })`
- mobile: `page.getByTestId("site-nav-menu").getByRole("link", { name: X, exact: true })`

## Why the desktop nav and the mobile menu never collide in the DOM

The desktop `<nav>` is `display:none` below `sm` (Tailwind `hidden`), so it is absent from the accessibility
tree and `getByRole` cannot see it. Base UI's `Popover.Portal` does not keep its content mounted when closed
(`keepMounted` defaults to false, see `components/ui/popover.tsx:29`), so the mobile links do not exist in the
DOM above `sm` or while the menu is shut. At any given viewport exactly one copy of the link set is reachable.

Playwright's default project is `devices["Desktop Chrome"]` (1280x720, `playwright.config.ts:20-23`), which is
above the `sm` 640px breakpoint — so the desktop nav is the default and the mobile branch must be exercised by
an explicit `page.setViewportSize({ width: 375, height: 812 })` before navigating.

## Presentational judgement call (delegated to the planner, now decided)

The anonymous link set renders on `/login` and `/signup` too, exactly as on every other route.

Rationale: `/search` is genuinely public and reachable without a session, and an anonymous visitor who lands on
`/login` has no other way to discover that browsing doctors is possible without an account. Suppressing the nav
on those two routes would require a pathname special-case inside a component whose entire value is being
route-agnostic, and would have to be maintained every time a public route is added. The header already renders
byte-identically on every route via the root layout; the nav follows that rule. The hamburger renders on mobile
for anonymous visitors too, holding its single link — a one-item menu is mildly redundant but strictly simpler
and more consistent than a link-count branch.
