## What Base UI actually does with `nativeButton` (verified in node_modules, not assumed)

`node_modules/@base-ui/react/internals/use-button/useButton.mjs`:

- **Lines 32-51 (dev only):** after mount, it compares the real DOM element against `isNativeButton`.
  It calls `error()` in BOTH directions — `nativeButton` true + non-`<button>` element, AND `nativeButton`
  false + `<button>` element. The fix must therefore not blanket-set `false`; it must key off `render`.
- **Lines 161-165:** `mergeProps(handlers, isNativeButton ? { type: 'button' } : { role: 'button' }, ...)`.
  This is the load-bearing consequence: **when `nativeButton` is false, Base UI adds `role="button"` to the
  rendered element.** On an `<a href>` that flips the accessible role from `link` to `button`.
- `@base-ui/utils/error.mjs` logs via `console.error("Base UI: " + message)` and **de-duplicates by exact
  message string in a module-scoped `Set`**. That Set is per browser-page-load. A test must therefore
  attach its console listener *before* any navigation and use a hard `page.goto()` on the asserted page,
  or a warning fired earlier in the same page session will be silently swallowed (false green).
- `props.render` is never injected by Base UI's own composition: `useRenderElement.mjs:104-129` clones the
  render element with `mergeProps(props, render.props)`, where neither side carries a `render` key. So in
  the reverse pattern (`PopoverTrigger render={<Button/>}`), `Button` receives no `render` prop, the new
  default resolves to `true`, and behavior is unchanged. Task 1 proves this empirically rather than
  trusting the reasoning.

## Type surface (verified)

`ButtonPrimitive.Props` extends `NativeButtonProps` (`nativeButton?: boolean | undefined`, default `true`)
and `BaseUIComponentProps<'button', ButtonState>` (`render?: React.ReactElement | ComponentRenderFn | undefined`).
Both props already exist on the wrapper's prop type — no type change is needed.
