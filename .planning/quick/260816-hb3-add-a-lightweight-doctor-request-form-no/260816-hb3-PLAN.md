## Migration

New file `supabase/migrations/20260816120000_add_doctor_requests.sql`. **Before writing it, run
`ls supabase/migrations/` and confirm `20260812090000_enable_notifications_realtime.sql` is still the latest —
if a newer file appeared, pick a timestamp that sorts after it instead.**

Table `public.doctor_requests`:

| column | type | notes |
|--------|------|-------|
| `id` | `uuid primary key default gen_random_uuid()` | mirrors every other table in the initial schema |
| `full_name` | `text not null` | |
| `email` | `text not null` | |
| `specialty_id` | `uuid references public.specialties (id) on delete set null` | nullable ON PURPOSE — see below |
| `message` | `text` | optional |
| `status` | `text not null default 'pending' check (status in ('pending', 'reviewed'))` | |
| `created_at` | `timestamptz not null default now()` | UTC, per the project timezone rule |

`specialty_id` is nullable so that deleting a specialty (the admin can do this) degrades a request row to
"no specialty" instead of blocking the delete or destroying the request. It is still **required at the
validation layer** — the form always sends one. Nullable column, required input; these are not in conflict.

Then `alter table public.doctor_requests enable row level security;` and three per-operation policies, matching
the granularity the initial schema already uses (`appointments_insert_patient` /
`appointments_update_own_or_admin` are separate policies, not one `for all`):

- `doctor_requests_insert_public` — `for insert with check (status = 'pending')`
- `doctor_requests_select_admin` — `for select using (public.is_admin())`
- `doctor_requests_update_admin` — `for update using (public.is_admin()) with check (public.is_admin())`

### The one deliberate deviation from the approved SQL — read this

The approved sketch wrote the insert policy as `with check (true)`. **Use `with check (status = 'pending')`
instead.** Rationale, to be recorded verbatim in the migration's own header comment:

Supabase grants `anon` table-level INSERT on new `public` tables by default (stated outright in
`20260811100000_revoke_appointments_direct_update.sql`'s header). So the browser can reach this table directly,
not only through the route. With `with check (true)`, anyone could insert a row that is **already marked
reviewed** — a row that would never appear in the admin's pending list and would silently defeat the entire
triage feature it exists to serve. Narrowing the check to `status = 'pending'` preserves the "anyone may submit"
intent byte-for-byte (the route inserts no `status` at all, so the column default supplies `'pending'` and RLS
WITH CHECK evaluates the post-default row) while removing the only client-controllable field that mattered. This
is strictly narrower than approved, never wider. It is the ONLY deviation from the approved SQL — the table
shape, the policy names, the per-operation split and the `public.is_admin()` reuse are all exactly as specified.

Apply with `npx supabase db push`, then confirm with `npx supabase migration list`. Docker-connection warnings
during push are expected in this environment and non-fatal (documented in 02-03 and 03-01 summaries). A
`Connection timed out` on the direct-DB step is a known IPv6/latency characteristic — retry once before treating
it as a real failure (02-01 summary).

## Validation module

New file `lib/validation/doctor-request.ts`. Single exported entry point
`validateDoctorRequestInput(body: Record<string, unknown>): string | null`, mirroring `validateDoctorInput`'s
single-string-return contract exactly. It **imports and calls** `validateFullName` and `validateEmail` from
`lib/validation/auth.ts` — do not re-implement either. Also export `validateSpecialtyId(value: unknown)` as a
named function so the dialog can field-map its message, mirroring how `doctors-page-client.tsx` maps messages to
fields.

Checks, in order, with these exact literal messages:

| condition | message |
|-----------|---------|
| `fullName` not a string, or `validateFullName` rejects it | (whatever `validateFullName` returned) |
| `fullName.trim().length > 200` | `Full name is too long.` |
| `email` not a string, or `validateEmail` rejects it | (whatever `validateEmail` returned) |
| `email.trim().length > 254` | `Invalid email format.` |
| `specialtyId` not a non-empty string | `Specialty is required.` |
| `message` present, not null, and not a string | `Message must be text.` |
| `message` a string longer than 2000 | `Message is too long.` |

The 2000 cap mirrors `lib/validation/availability.ts:81`'s existing `reason` cap — same reasoning, same number,
so the codebase has one answer to "how long is too long for a free-text field". 254 is the RFC 5321 maximum
address length, and reusing the existing `Invalid email format.` literal rather than inventing a new one is
deliberate: an over-length address genuinely is an invalid address, and it keeps the dictionary smaller.

`Specialty is required.` is intentionally byte-identical to `lib/validation/doctor.ts:14`'s literal. That module
never routes through `translateValidationMessage`, so sharing the string cannot change any admin copy.

## Public POST route

New file `app/api/doctor-requests/route.ts`. **No auth guard** — this is the first and only unauthenticated write
endpoint in the application. Shape:

1. `const body = await request.json()`
2. `validateDoctorRequestInput(body)` -> 400 with `{ error }` on failure
3. Build the insert object from **four explicitly named fields only** — `full_name`, `email`, `specialty_id`,
   `message`. Never spread the body. `status`, `id` and `created_at` come from column defaults and are never read
   from request input. Add a comment saying exactly that, in the voice of
   `app/api/admin/doctors/route.ts:83-85`'s `is_active, is_demo and profile_id are never read from the request
   body` note and `app/api/auth/signup/route.ts`'s hardcoded-`role` note.
4. `await supabase.from("doctor_requests").insert({...})` through `lib/supabase/server.ts`'s `createClient()` —
   the session-bound client, NOT `lib/supabase/admin.ts`. **Chain nothing after `.insert()`.**
5. On a Postgres `23503` (foreign-key violation, i.e. a `specialtyId` that does not exist), return 400 with
   `Specialty is required.` — branch on `error.code`, never on `error.message`, the rule every route in this
   project follows. On any other error return 500 with `Could not send your request. Please try again.`
6. On success return `NextResponse.json({ ok: true }, { status: 201 })`.

Trim behaviour: store `full_name` and `email` trimmed (they are identity fields where surrounding whitespace is
never meaningful); store `message` **exactly as submitted, untrimmed** — `trim()` is used only to test blankness.
That is the Phase 04 `reason` rule (04-03 Rule 1 fix), applied to the one free-text field here for the same
reason. An empty-or-whitespace-only `message` is stored as `null`, not `""`.

## Admin API routes

`app/api/admin/doctor-requests/route.ts` — `GET` only. `requireAdmin()` guard first (`if (!guard.ok) return
guard.response`), then select through `guard.supabase`:

```
"id, full_name, email, message, status, created_at, specialty:specialties(id,name_en,name_he)"
```

ordered `created_at` descending then `id` descending — the same stable two-key ordering
`app/api/admin/doctors/route.ts:49-50` uses so equal timestamps never shuffle between reloads. Return
`{ requests: [...] }`. On error, 500 with `Could not load doctor requests. Please refresh the page.`

`app/api/admin/doctor-requests/[id]/route.ts` — `PATCH` only, `{ params }: { params: Promise<{ id: string }> }`,
`const { id } = await params` (the Next 16 shape used by every existing `[id]` route here). `requireAdmin()`
first. **Parse no body at all** — the action is implicit in the endpoint, so the handler signature takes
`_request: Request` and never calls `request.json()` (calling it on an empty body throws). Then:

```
.from("doctor_requests").update({ status: "reviewed" }).eq("id", id).select("id")
```

Zero returned rows -> 404 `Doctor request not found.` (see key_links — this is the 04-02 lesson). Error -> 500
`Could not update this request. Please try again.` Success -> `{ ok: true }`. The operation is deliberately
one-way and idempotent: a second PATCH on an already-reviewed row still matches, still writes `'reviewed'`, and
still returns 200. There is no un-review action.
