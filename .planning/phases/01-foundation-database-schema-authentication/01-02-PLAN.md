<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `POST /api/auth/signup` | Fully untrusted JSON crosses here; the body is attacker-controlled |
| Route Handler -> Supabase (service role) | The admin client bypasses every RLS policy, so anything it writes is unchecked by the database |
| Route Handler -> Supabase (anon/session) | RLS applies; `profiles` policies check `id = auth.uid()` only |
| browser bundle boundary | Anything imported transitively by a Client Component can be shipped to the browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Elevation of Privilege | `app/api/auth/signup/route.ts` | critical | mitigate | The `profiles` INSERT policy checks only `id = auth.uid()` and never constrains the privilege column, so the handler writes the row through `createAdminClient()` with the value `"patient"` written inline in the insert object and destructures only `email`, `password`, `fullName` from the body. Proven by the direct-POST test in Task 1 that sends a privilege field and asserts it was ignored |
| T-01-06 | Information Disclosure | `lib/supabase/admin.ts` | high | mitigate | `import "server-only"` turns any Client Component import into a build error; the key is read from `SUPABASE_SERVICE_ROLE_KEY`, deliberately not `NEXT_PUBLIC_`-prefixed, so Next.js cannot inline it into the browser bundle. Gated by a negative grep over `lib`, `app` and `components` |
| T-01-04 | Spoofing | `app/patient/layout.tsx` | high | mitigate | The role decision uses the network-verified `auth.getUser()`; the unrevalidated cookie-read accessor is banned repo-wide by a negative grep over `app` and `lib` |
| T-01-05 | Information Disclosure | `app/api/auth/signup/route.ts` | high | mitigate | The service-role client is used only to create the account and insert that user's own `profiles` row. No user-facing read is routed through it, so RLS (`profiles_select_own_or_admin`) stays the boundary for every read |
| T-01-11 | Denial of Service | `app/api/auth/signup/route.ts` | low | accept | Unauthenticated signup can be called repeatedly. Supabase Auth's per-IP rate limit is the control and the developer confirms it in Plan 01's `user_setup`; adding app-level throttling is not covered by any AUTH-01..07 requirement and the platform control is sufficient for a demo-scale deployment |
| T-01-12 | Tampering | orphaned `auth.users` rows | low | mitigate | If the `profiles` insert fails after the auth account was created, the handler deletes the just-created user, so a partial signup cannot leave a login account with no role row |
</threat_model>
