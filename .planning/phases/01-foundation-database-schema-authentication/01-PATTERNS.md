### `lib/supabase/server.ts` (service, request-response)

**No in-repo analog — use RESEARCH.md Pattern 2 verbatim.** Key correction already baked in: `cookies` imports from `"next/headers"` (NOT `"next/handlers"` — a hallucination the research explicitly caught and fixed). File is `async` and must be awaited by every caller (`const supabase = await createClient();`).

```typescript
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";

export async function createClient() {
  const cookieStore = await cookies();
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() { return cookieStore.getAll(); },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options));
          } catch { /* safe to ignore, proxy.ts refreshes session every request */ }
        },
      },
    },
  );
}
```
Source: `01-RESEARCH.md` "Pattern 2: Server client".

### `proxy.ts` (repo root) + `lib/supabase/proxy.ts` (middleware, request-response)

**No in-repo analog. CRITICAL naming pitfall (Pitfall 1 in RESEARCH.md): the file MUST be named `proxy.ts`, NOT `middleware.ts`.** Next.js 16.0.0 renamed the convention; `middleware.ts` is silently ignored with no build error. Use RESEARCH.md Pattern 4 verbatim for both files (root `proxy.ts` delegates to `lib/supabase/proxy.ts`'s `updateSession()`).

Root `proxy.ts`:
```typescript
import { updateSession } from "@/lib/supabase/proxy";
import { type NextRequest } from "next/server";

export async function proxy(request: NextRequest) {
  return await updateSession(request);
}

export const config = {
  matcher: [
    "/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)",
  ],
};
```

`lib/supabase/proxy.ts` — full `updateSession()` implementation is in RESEARCH.md "Pattern 4" (role-prefix matcher for `/patient`, `/doctor`, `/admin`; uses `getUser()`, never `getSession()`; redirects unauthenticated users to `/login`). Role-mismatch enforcement is deliberately deferred to the layout files (Pattern 5) to avoid an extra DB round-trip per request — do not duplicate that check in `proxy.ts`.

**Also apply Pitfall 3:** `app/patient/`, `app/doctor/`, `app/admin/` must be **plain folders**, not Next.js route groups (`(patient)` etc.) — route groups don't appear in the URL and would break both the `proxy.ts` matcher and the TASKS.md-specified redirect targets (`/patient/dashboard`, `/doctor/dashboard`, `/admin`).

**Logic content: use RESEARCH.md "Manual validation functions (D-02)" verbatim** (no analog exists in-repo for validation logic since D-02 explicitly rejects a schema library):
```typescript
export function validateEmail(email: string): string | null {
  const trimmed = email.trim();
  if (!trimmed) return "Email is required.";
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(trimmed)) return "Invalid email format.";
  return null;
}

export function validatePassword(password: string): string | null {
  if (!password) return "Password is required.";
  if (password.length < 6) return "Password must be at least 6 characters.";
  return null;
}

export function validateFullName(fullName: string): string | null {
  if (!fullName.trim()) return "Full name is required.";
  return null;
}
```
Error copy strings must match `01-UI-SPEC.md`'s Copywriting Contract exactly (already aligned above).

### `app/api/auth/signup/route.ts` (controller, request-response)

**No in-repo analog — use RESEARCH.md "Signup Route Handler" verbatim** (closes both Pitfall 2 — RLS does not restrict `profiles.role`, so `role` must be hardcoded server-side via the admin client — and Pitfall 4 — remote project's email-confirmation setting is unverified, so use `admin.createUser({ email_confirm: true })` instead of the anon `signUp()`). Full code block is in RESEARCH.md "Code Examples" section (imports `createClient` from `lib/supabase/server`, `createAdminClient` from `lib/supabase/admin`, and the three validators from `lib/validation/auth`).

**Core pattern shape:**
1. Parse body, run manual validators, 400 on any error.
2. `createAdminClient().auth.admin.createUser({ email, password, email_confirm: true })`.
3. `admin.from("profiles").insert({ id, role: "patient", full_name, email })` — role hardcoded, never from `body`.
4. `createClient()` (server SSR client) → `signInWithPassword()` so `Set-Cookie` lands on the response.
5. Return `{ success: true }`.

### `app/api/auth/login/route.ts` and `app/api/auth/logout/route.ts` (controller, request-response)

**No in-repo analog — use RESEARCH.md "Login / Logout Route Handlers" verbatim.** Login: validate → `signInWithPassword()` → 401 generic "Invalid credentials." on any failure (do not leak which field was wrong) → fetch `profiles.role` → return `{ success, role }` so the client can redirect appropriately. Logout: `createClient()` → `signOut()` → `{ success: true }`.

### `app/patient/layout.tsx`, `app/doctor/layout.tsx`, `app/admin/layout.tsx` (provider/layout, request-response)

**Structural analog:** `app/layout.tsx` (existing root layout) — establishes the convention of an `async function` default export taking `{ children }: { children: React.ReactNode }`.
```typescript
// app/layout.tsx:20-24
export default function RootLayout({
  children,
}: Readonly<{
  children: React.ReactNode;
}>) {
```
Root layout is currently NOT async (no data fetching); role layouts must be `async` since they call `supabase.auth.getUser()`.

**Logic content: use RESEARCH.md "Pattern 5: Role-scoped layout" verbatim,** swapping the literal role string per file (`'patient'` / `'doctor'` / `'admin'`):
```typescript
import { redirect } from "next/navigation";
import { createClient } from "@/lib/supabase/server";

export default async function PatientLayout({ children }: { children: React.ReactNode }) {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) redirect("/login");

  const { data: profile } = await supabase
    .from("profiles").select("role").eq("id", user.id).single();

  if (profile?.role !== "patient") redirect("/");

  return <>{children}</>;
}
```
This is defense-in-depth against `proxy.ts` (which only checks auth presence, not role) and is itself backstopped by RLS (`is_admin()`, `is_doctor_owner()`).

## Shared Patterns

### Supabase SSR cookie sync (applies to `server.ts`, `proxy.ts`, every Route Handler and role layout)
**Source:** RESEARCH.md Patterns 2 & 4
Always use `getUser()` (network-verified), never `getSession()` (unrevalidated), for any authorization decision. Never insert other code between `createServerClient(...)` and `getUser()` in `proxy.ts` — both official examples warn this can cause random logouts.

### Role hardcoding on privileged writes (applies to `signup/route.ts`, any future profile-update endpoint)
**Source:** RESEARCH.md Pitfall 2
`profiles` RLS does not constrain the `role` column (`id = auth.uid()` is the only check on both insert and update policies — `supabase/migrations/20260803230000_initial_schema.sql:200-204`). Never accept `role` from client-supplied JSON in any Route Handler; always hardcode server-side or derive it via the admin client.

### Manual validation error shape (applies to all three Route Handlers + both form pages)
**Source:** RESEARCH.md "Manual validation functions (D-02)" + `01-UI-SPEC.md` Copywriting Contract
Validators return `string | null` (error message or null = valid). Route Handlers return `{ error: string }` with the first non-null validator message, HTTP 400. Client forms mirror the same validators for instant inline feedback before the network call (UX only, not the security boundary — server always re-validates).

### `NextResponse.json` response shape (applies to all `app/api/auth/*` routes)
**Source:** RESEARCH.md Code Examples
Success: `{ success: true }` (logout), `{ success: true }` (signup), `{ success: true, role }` (login). Error: `{ error: string }` with an appropriate status code (400 validation, 401 invalid credentials, 500 unexpected).

### Open-redirect guard on `?from=` (applies to `proxy.ts` and `login/page.tsx`)
**Source:** RESEARCH.md Security Domain
Validate the `from` query param is a same-origin relative path (`startsWith('/')`, not `startsWith('//')`, no scheme) before using it as a post-login redirect target.
