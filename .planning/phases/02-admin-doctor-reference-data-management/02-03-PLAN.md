<interface_contract>
`lib/validation/reference-data.ts`:
```
export function validateSpecialtyInput(body: Record<string, unknown>): string | null;
export function validateLocationInput(body: Record<string, unknown>): string | null;
```
Both return "Name is required." for a blank required name field, mirroring the
`string | null` style of `lib/validation/auth.ts`.

Endpoints (every `[id]` handler takes `{ params }: { params: Promise<{ id: string }> }` and reads
the id with `const { id } = await params;` — Next.js 16 route params are a Promise):

- `GET /api/admin/specialties` → 200 `{ specialties: { id, name_he, name_en, doctorCount }[] }`
- `POST /api/admin/specialties` body `{ nameEn, nameHe }` → 201 `{ specialty }` · 400 `{ error }` · 409 `{ error }` on duplicate
- `PATCH /api/admin/specialties/[id]` body `{ nameEn?, nameHe? }` → 200 `{ specialty }` · 404 · 409 on duplicate
- `DELETE /api/admin/specialties/[id]` → 200 `{ success: true }` · 404 · 409 `{ error, doctorCount }` when referenced
- `GET /api/admin/locations` → 200 `{ locations: { id, city, neighborhood, address, doctorCount }[] }`
- `POST /api/admin/locations` body `{ city, neighborhood, address? }` → 201 `{ location }` · 400 · 409
- `PATCH /api/admin/locations/[id]` body `{ city?, neighborhood?, address? }` → 200 `{ location }` · 404 · 409
- `DELETE /api/admin/locations/[id]` → 200 `{ success: true }` · 404 · 409 `{ error, doctorCount }`

`doctorCount` is the number of `doctors` rows referencing that reference-data row; the client uses
it to disable the delete control and render the D-05 inline explanation.
</interface_contract>

<task type="checkpoint:decision" gate="blocking">
  <name>Checkpoint: lock the reference-data uniqueness tuple before the migration ships</name>
  <decision>The uniqueness tuple for `public.locations` (and confirmation of `unique (name_en)` on `public.specialties`)</decision>
  <context>
    The demo-data seed script (plan 02-06) must be safely re-runnable. The idiomatic way to get
    that is a natural-key unique constraint plus `insert ... on conflict do nothing`, but
    `specialties` and `locations` have no unique constraint today.

    This is a one-way door. Once the constraint ships to the remote hosted project, changing its
    shape requires another migration, and if the tuple is too narrow it will reject legitimate rows
    the admin genuinely wants — 02-RESEARCH.md assumption A2 flags exactly this at Medium risk:
    two real Tel-Aviv practice addresses can sit in the same neighborhood of the same city.
    Phases 3-6 read `locations` for search filtering, so the shape chosen here is inherited by
    every later phase.

    `unique (name_en)` on `specialties` is the low-risk half — specialty names are genuinely
    unique — and is recommended unchanged. The locations tuple is the real decision.
  </context>
  <options>
    <option id="option-a">
      <name>unique (neighborhood, city) on locations — the RESEARCH.md recommendation</name>
      <pros>Simplest natural key; makes "one row per Tel-Aviv neighborhood" literally true, which matches D-07's "all Tel-Aviv neighborhoods represented" demo dataset and Phase 3's neighborhood filter; `on conflict` seeding works with no extra logic.</pros>
      <cons>Two distinct practice addresses inside the same neighborhood cannot both exist as locations; if the app later needs per-address locations this needs a new migration.</cons>
    </option>
    <option id="option-b">
      <name>unique (city, neighborhood, address) on locations</name>
      <pros>Allows several addresses within one neighborhood, which is closer to how a real clinic directory works.</pros>
      <cons>`address` is nullable and Postgres treats NULLs as distinct by default, so any row with a null address escapes the constraint entirely — the seed script's idempotency guarantee silently breaks for exactly the rows D-07 seeds; would require `nulls not distinct` or a not-null default to be sound.</cons>
    </option>
    <option id="option-c">
      <name>No unique constraint on locations; the seed script guards duplicates itself</name>
      <pros>No schema commitment at all; nothing to migrate away from later.</pros>
      <cons>Idempotency becomes a check-then-insert in application code, which 02-RESEARCH.md flags as the documented race-prone anti-pattern; nothing stops the admin UI creating a duplicate neighborhood either.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>
</task>
