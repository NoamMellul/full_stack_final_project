    Add `"seed": "tsx scripts/seed.ts"` to the `scripts` block of `package.json`.

    Write `scripts/seed.ts`. It loads `.env.local` with `loadEnvConfig(process.cwd())` from
    `@next/env` (already a transitive dependency, used the same way by `playwright.config.ts`),
    then builds a service-role client directly with `createClient` from `@supabase/supabase-js`
    using `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, throwing a clear error naming
    the missing variable if either is absent. It does not import `lib/supabase/admin.ts`, which is
    marked `server-only` and would fail outside a Next.js runtime.

    The script performs these steps in order, using only inserts and upserts. It contains no
    row-removal call and no table-truncation statement against any table — the whole point of an
    idempotent seeder is that a second run is a no-op, never a reset. That constraint is what keeps
    the script safe to run against a database holding data it did not create.

    1. **Specialties.** Upsert the full catalog with `{ onConflict: "name_en", ignoreDuplicates:
       true }`, targeting the unique constraint plan 02-03's migration added. Cover the specialties
       a Tel-Aviv private-practice directory would realistically list — family medicine,
       cardiology, dermatology, paediatrics, gynaecology, orthopaedics, ophthalmology,
       otolaryngology, gastroenterology, psychiatry and similar — each with both a Hebrew and an
       English name, since `name_he` and `name_en` are both non-null columns.
    2. **Locations.** Upsert the full set of Tel-Aviv neighborhoods with the conflict target
       matching the tuple plan 02-03's checkpoint selected. All neighborhoods in the catalog must be
       represented (D-07). City is Tel-Aviv throughout.
    3. **Doctors.** Build a list of 12 demo doctors (inside D-07's 10-15 envelope) with realistic
       Hebrew and English names and one- or two-sentence bios, distributed so that every specialty
       is used by at least one doctor and every neighborhood has at least one doctor. Set
       `is_active: true` explicitly — the column defaults to `false`, and Phase 3's public search
       reads only active doctors, so an inactive demo catalog would be invisible. Leave `is_demo`
       to its `true` default and never set it otherwise. Leave `photo_url` null for every one of
       them (D-08) so the dataset pulls in no external asset and exercises the initials-avatar
       fallback. Because `doctors` has no natural unique key, guard idempotency at the script level:
       before inserting, read the existing demo doctors and skip any whose `full_name` already
       appears among rows with `is_demo` true.
    4. **Doctor languages.** For each doctor actually inserted, insert `doctor_languages` rows
       linking it to Hebrew, English, or both — with a deliberate mix so Phase 3's language filter
       has doctors on each side of it. Skip any doctor that was already present.
    5. **Demo patients.** Create four demo patient accounts through `auth.admin.createUser` with
       `email_confirm: true` and a fixed, obviously-demonstration password, then insert their
       `profiles` rows with `role: "patient"` hardcoded in the script. Guard by looking up the
       email in `profiles` first and skipping when it already exists, so a re-run creates nothing.
       Do not create any account with the admin role — admin bootstrapping is a deliberate
       out-of-band act, not something a seed script should hand out.
    6. **Summary.** Print exactly one final line in the fixed form
       `seed complete: specialties=<n> locations=<n> doctors=<n> doctor_languages=<n> patients=<n>`,
       where each number is the total row count in that table after the run — not the number this
       run inserted. Reading totals rather than deltas is what makes two consecutive runs print an
       identical line, which is the automated idempotency assertion in Task 2.

    Exit with a non-zero status and a readable message on any database error, so a failed seed is
    never mistaken for a successful one.
  </action>
