<interface_contract>
- `POST /api/admin/doctors/[id]/link-account` body `{ email: string }`
  → 201 `{ tempPassword: string, email: string }`
  · 400 `{ error }` on an invalid email
  · 404 `{ error: "Doctor not found." }`
  · 409 `{ error: "This doctor is already linked to a login account." }`
  · 400 `{ error: "An account with this email already exists." }` on a duplicate email
  · 500 `{ error: "Could not create a login for this doctor. Please try again." }`
  Signature `(request: Request, { params }: { params: Promise<{ id: string }> })`; id via
  `const { id } = await params;` (Next.js 16 route params are a Promise).

- `POST /api/auth/change-password` body `{ password: string, confirmPassword: string }`
  → 200 `{ success: true }` · 400 `{ error }` · 401 when unauthenticated
  · 500 `{ error: "Could not update password. Please try again." }`

  <action>
    Write `supabase/migrations/20260804120200_add_must_change_password.sql` with two parts.

    First: `alter table public.profiles add column must_change_password boolean not null default
    false;`. The default is deliberately `false`. Defaulting it to `true` would sweep in every
    existing row and every future patient self-signup through `/api/auth/signup`, forcing a
    password change on users who never needed one (RESEARCH Pitfall 1). Only the link-account route
    sets it `true`, and it does so explicitly on insert.

    Second: lock down which columns an ordinary logged-in user may update on their own profile row.
    `profiles_update_own_or_admin` is a row-level policy with no WITH CHECK clause, so its USING
    expression governs the check too — meaning a logged-in user can currently write any column of
    their own row, including the new flag and their own `role`. Row-level policies cannot express
    column scope, so use column-level grants:
    `revoke update on public.profiles from authenticated;` followed by
    `grant update (full_name, email) on public.profiles to authenticated;`. Revoking the
    table-level privilege first is required — a column-level REVOKE does not remove a table-level
    grant. No existing code path updates `profiles` through the session-bound client (verified: only
    `select` calls exist in `app/*/layout.tsx` and `app/api/auth/login/route.ts`), and the
    service-role client is unaffected by these grants, so nothing in the app breaks. Apply with
    `npx supabase db push`.

    Create `app/api/admin/doctors/[id]/link-account/route.ts` exporting `POST`. Signature
    `(request: Request, { params }: { params: Promise<{ id: string }> })`, id via
    `const { id } = await params;`.

    Order of operations:
    1. `const guard = await requireAdmin(); if (!guard.ok) return guard.response;` — no Supabase
       Auth call happens before this returns ok.
    2. Read `email` from the body and validate it with `validateEmail`; 400 on failure.
    3. Build the service-role client with `createAdminClient()`. This is the one route in the phase
       that structurally requires it: `auth.admin.createUser()` has no session-client equivalent,
       and inserting a profiles row whose `id` is another user's id fails the
       `profiles_insert_own` policy.
    4. Read the doctor by id; 404 `{ error: "Doctor not found." }` when absent. When its
       `profile_id` is already set, return 409 `{ error: "This doctor is already linked to a login
       account." }` and stop — no auth user is created, which is what makes a repeat call a no-op.
    5. Generate the temporary password with `randomBytes(12).toString("base64url")` from
       `node:crypto`. A non-cryptographic random source is not acceptable for a credential.
    6. `admin.auth.admin.createUser({ email, password: tempPassword, email_confirm: true })`.
       On failure, reuse the duplicate-detection block from `app/api/auth/signup/route.ts` verbatim
       and return "An account with this email already exists." for that case — and critically, do
       not delete anything on this branch, since the existing account belongs to whoever created it
       first. Any other failure returns 500 with "Could not create a login for this doctor. Please
       try again.".
    7. Insert the profiles row `{ id: created.user.id, role: "doctor", full_name: doctor.full_name,
       email, must_change_password: true }`. `role` is a server-side literal here exactly as
       `app/api/auth/signup/route.ts` hardcodes `"patient"` — it is never read from the request
       body (T-02-01). If this insert fails, delete the just-created auth user with
       `admin.auth.admin.deleteUser(created.user.id)` so no orphaned login is left, then return 500.
    8. `admin.from("doctors").update({ profile_id: created.user.id }).eq("id", id)`. If this fails,
       delete the auth user and the profiles row and return 500 — a doctor row must never be left
       pointing at nothing while an account exists for it.
    9. Return 201 `{ tempPassword, email }`.

    The generated password appears in exactly one place — this response body. It is never written to
    any log sink, never stored in a database column, and never included in an error message. The
    flag it pairs with lives in the `profiles` table column added above, never in Supabase Auth's
    client-editable metadata bag, which is not a safe place for an authorisation decision (T-02-04).
  </action>
