- **NOTIF-01, NOTIF-02, NOTIF-03 and NOTIF-04 edge probes all returned `unclassified`** (spec-less probe fallback, §A). The engine generated no specific edge questions for the four notification requirements, so all four rows stay **unresolved** rather than being auto-dismissed. Planner assumption carried forward: the genuinely reachable edges are (a) the same event producing two rows with the same `type` for two different recipients, resolved by the viewer-role key derivation owned by 06-06; (b) a notification arriving while the dropdown is already open, locked by the UI-SPEC to render unread until the dropdown is reopened; and (c) a Realtime event delivered after the session token has been refreshed, which is Assumption A1 below. Surface all four at verify time; do not treat them as covered without evidence.
- **RESEARCH Assumption A1** (`createBrowserClient`'s Realtime auth token refresh is automatic, with no manual `realtime.setAuth()` call needed) is community-sourced, not official-docs-verified. If a long-lived bell session silently stops receiving events, the cheap mitigation is an explicit `onAuthStateChange` listener calling `realtime.setAuth()`. Carried into 06-06.
- **A correction to CONTEXT.md's `<specifics>` section**: the database stores exactly three `notifications.type` values, not six. Each event inserts the same `type` twice — once for the patient, once for the doctor — with different, never-rendered `message` text. `notifications.type` is a plain `text` column with no check constraint, so it is an open enum from the reader's perspective.
