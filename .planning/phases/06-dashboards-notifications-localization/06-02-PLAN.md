    Create `app/api/patient/favorites/route.ts` with `POST` and `GET`, both opening with `const guard = await requirePatient(); if (!guard.ok) return guard.response;`.

    `POST` parses the JSON body, runs `validateFavoriteInput`, returns 400 with `{ error: <message> }` on failure, then inserts `{ patient_id: guard.userId, doctor_id: doctorId }` into `favorites` through `guard.supabase`. `patient_id` is always taken from `guard.userId` and never from the request body — a client-supplied `patientId` must be inert. Branch on `error.code === "23505"` for the unique-violation and return 409 with `"This doctor is already in your favorites."`; any other error returns 500 with `"Could not update your favorites. Please try again."`; success returns 201 with `{ ok: true }`.

    `GET` runs a two-step read, mirroring the Phase 3 precedent of reducing a pre-query to an id list and re-querying with `.in()` rather than relying on a PostgREST embed across a view boundary. Step one selects `id, doctor_id, created_at` from `favorites` with `.eq("patient_id", guard.userId)`, `.order("created_at", { ascending: false })` and `.order("id", { ascending: false })` — the id tiebreaker is what makes the order stable when two rows share a `created_at`. Step two selects the full `doctor_search_view` column set for `.in("id", <doctor ids from step one>)`, skipped entirely when step one returned zero rows. Merge in JavaScript preserving step one's order, emitting `{ favorites: [{ id, doctor_id, created_at, doctor }] }` where `doctor` is the matching view row or `null` when the doctor is inactive (the view filters `is_active = true`). Either query erroring returns 500 with `"Could not load your favorites. Please try again."`. An empty result is a 200 with `{ favorites: [] }`, never a 404.

    Create `app/api/patient/favorites/[id]/route.ts` with `DELETE`, where `[id]` is the `doctors.id` being un-favorited (not the `favorites.id`) — this matches the toggle's by-doctor-id UX and avoids a lookup round trip. Guard with `requirePatient()`, reject a non-UUID id with the same 404 body used for a genuinely missing row, then delete with `.delete({ count: "exact" }).eq("patient_id", guard.userId).eq("doctor_id", id)`. Both scoping conditions live in the delete's own WHERE clause together — never delete by doctor id alone followed by a separate ownership comparison. `count === 0` returns 404 with `"This doctor is not in your favorites."`; that single message is shared by the missing, already-deleted, and foreign-patient cases so the response cannot confirm another patient's favorite exists. A driver error returns 500 with `"Could not update your favorites. Please try again."`; success returns 200 with `{ ok: true }`.
