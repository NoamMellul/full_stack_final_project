<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dictionary value → rendered DOM | Every translated string becomes a React child on a user-facing page |
| validator message → translated output | A message string is used as a lookup identifier, so an unmapped or attacker-influenced string must degrade safely |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-32 | Tampering | XSS through a dictionary value | medium | mitigate | All dictionary values are repo-authored static strings rendered as React children; no interpolation syntax and no `dangerouslySetInnerHTML` is introduced anywhere in this phase |
| T-06-33 | Information Disclosure | validation messages leaking internal detail once translated | low | mitigate | Only the existing user-facing messages are mapped; no new message text is invented, so the translated surface is exactly the surface Phases 1-5 already shipped |
| T-06-34 | Tampering | an unmapped validator message rendering as blank | medium | mitigate | `translateValidationMessage` returns the original message unchanged when unmapped, so the degradation is readable English rather than an empty or key-path field error |
| T-06-35 | Information Disclosure | an untranslated Hebrew value silently shipping as English | low | mitigate | A parity check plus an equal-value scan run as acceptance criteria; any surviving equal pair must be justified in the SUMMARY as genuinely language-neutral |
| T-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package-manager install occurs in this plan; the dictionaries are repo-authored JSON |
</threat_model>
