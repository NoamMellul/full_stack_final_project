<objective>
Prove, not assert, that the database is the thing preventing an invalid schedule. Every conflict rule in this phase is enforced by one Postgres exclusion constraint; the application only translates its failure. This plan drives that constraint directly under concurrency and across every status pairing, and separately sweeps the ownership and visibility boundary so a doctor's schedule — and the private note attached to a block — cannot leak or be written across doctors.

Purpose: PROJECT.md's core commitment is a database-level guarantee that two writes can never both win, and STATE.md records that it "must be explicitly tested, not just asserted". Phase 5 makes that claim about `appointments`; this plan makes the same claim about `availability_slots`, which is the table Phase 5 will build on. An application-only overlap check that looks correct in single-threaded tests is exactly the failure mode this catches.

Output: `tests/e2e/doctor-schedule-overlap.spec.ts` and `tests/e2e/doctor-schedule-visibility.spec.ts`, plus any hardening the specs prove is missing in the three route handlers.

Scope guard: these specs assert against the routes as plans 04-01 through 04-03 built them. If a case fails, fix the route rather than weakening the assertion — the assertions encode the locked decisions, not a preference.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| doctor session -> another doctor's rows | The ownership boundary, swept here in all four directions: add, block, delete and list |
| anonymous / patient session -> `availability_slots` | The public-read boundary; the phase's new `reason` column sits behind it |
| any write path -> a `booked` row | The boundary protecting a patient's appointment from a doctor's schedule edit |
| two concurrent writes -> the same time range | The integrity boundary the exclusion constraint owns |
