<objective>
Deploy the one schema change this phase needs, then prove the entire doctor-availability path end to end on the thinnest real slice: a doctor opens their own schedule page, adds one available time slot, and sees it appear. Every layer this phase will later expand into — session-resolved doctor ownership, manual validation, the REST route, the Postgres constraint translation, the Asia/Jerusalem conversion, and the day-grouped list — is wired for keeps on that single path.

Purpose: an architectural dead-end in this stack (ownership resolution, timezone conversion, or the `23P01` translation this codebase has never done before) is found after one commit instead of after four. Everything built here is production-quality and stays; nothing is a prototype.

Output: the `availability_slots.reason` migration applied to the remote database, `requireDoctor()`, `lib/validation/availability.ts`, `GET`/`POST /api/doctor/slots`, the `/doctor/schedule` page, and the add-slot end-to-end spec.

Scope guard: availability management is doctor-only this phase (D-05) — no `app/api/admin/**/slots` route and no admin schedule page is created here. Booking is Phase 5; this plan never reads or writes `appointments`.

Recurring / bulk slot generation (D-16, Claude's discretion): assessed and NOT built. A "repeat weekly for N weeks" convenience would fire N independent inserts against a constraint that can reject any subset of them, which means partial-success reporting and a per-row error surface — that is not trivial on top of the single-slot form, so the discretion is exercised against it.
</objective>
