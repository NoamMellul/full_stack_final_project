<objective>
Let a doctor take time off the board: a single continuous blocked period with an optional note, created through its own form, rejected by the database whenever it collides with anything already on the schedule. This closes AVAIL-06 and, together with the exclusion constraint the add-slot route already leans on, AVAIL-07.

Purpose: blocking is the second write path into `availability_slots`, and it is where the phase's "one mechanism, uniformly applied" design either holds or fragments. The same guard, the same validator conventions, the same `23P01` translation and the same generic message are reused rather than re-derived, so a blocked period and an available slot cannot drift apart in behaviour.

Output: `validateBlockedPeriodInput`, `POST /api/doctor/blocked-periods`, the Block period dialog and blocked-row reason rendering on `/doctor/schedule`, and the block-period e2e spec.

Scope guard: a blocked period is one row (D-03). No per-day expansion, no recurrence, no business-hours decomposition. Un-blocking is deleting the row via plan 04-02's endpoint (D-01) — this plan adds no un-block route and no status toggle.
</objective>
