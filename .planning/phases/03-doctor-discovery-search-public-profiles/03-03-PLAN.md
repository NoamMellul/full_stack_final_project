<objective>
Prove the entire doctor-discovery architecture end to end with one thin slice — an anonymous visitor searching by name at `/search` and getting real, sorted, server-paginated results out of `doctor_search_view` — then build the result presentation out from that proven path.

Purpose: this phase introduces three things the codebase has no precedent for at once (a public unauthenticated REST route, a view-backed query, and server-side pagination). Wiring one filter through all of them first means an architectural dead end surfaces after one commit rather than after every filter, the profile page, and the pagination UI have all been built on top of it.

Output: a working `/search` page, the `GET /api/doctors` endpoint with its validation module, the result card and grid components with all four render states, and the first of this phase's Playwright specs.

## Planner assumptions (flagged, not dismissed)

- **SEARCH-01 / encoding — Unicode normalization form is unspecified.** No source artifact (REQUIREMENTS.md, 03-CONTEXT.md, 03-RESEARCH.md, 03-UI-SPEC.md) states whether `q` or the stored `full_name` is normalized to NFC or NFD before comparison. This plan applies no normalization on either side, which means a Hebrew query typed in a different normalization form than the stored value will not match. Accepted for a demo dataset whose names are seeded in a single form; surfaced here so a future phase that accepts user-authored doctor names can decide deliberately.
- **Canon-referral breadcrumbs (prohibition probe, Stage 2).** SQL injection through search parameters and RLS/access-control bypass on the public routes are canon security items owned by `/gsd-secure-phase` and the `<threat_model>` rows T-03-01 / T-03-02 / T-03-03 above; they are not minted as project-specific prohibitions. Retention and consent for patient search terms (a specialty query is a health inference about the searcher) is canon GDPR, likewise referred to `/gsd-secure-phase` and not minted.
