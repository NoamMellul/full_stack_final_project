<objective>
Create the `doctor_search_view` Postgres view that every patient-facing search query in this phase reads from, push it to the live Supabase project, and prove with an anonymous client that it inherits the existing RLS protections instead of bypassing them.

Purpose: sorting a doctor list by "soonest next available slot" and filtering it by spoken language are both computations over child tables. Neither is expressible through the Supabase query builder against `public.doctors` alone. A `security_invoker` view flattens both into plain columns so the whole search — filter, sort with nulls last, and server-side `.range()` pagination — becomes one query builder call (RESEARCH.md Pattern 1). This plan is a hard dependency for every other plan that touches `/search`.

Output: one migration file applied to the remote database, and one Playwright spec that fails if the view ever starts leaking inactive doctors or unavailable slots.
</objective>
