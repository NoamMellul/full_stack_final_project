<objective>
Give the search results the numbered pagination the phase's decisions call for, and prove that paging never duplicates, skips, or reshuffles a doctor.

Purpose: the API has paged server-side since the tracer, but the page has only ever shown page 1. This plan adds the navigation, the total count, and — more importantly — the automated proof that the sort contract holds across separate paginated requests. RESEARCH.md Pitfall 4 is specifically about the two ways this breaks silently: an off-by-one offset that shifts every page, and a non-deterministic tie order that lets the same doctor appear on two pages.

Output: pagination controls with the ellipsis overflow behaviour, the total-count caption, and the phase's last Playwright spec.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04 | Denial of Service | The `page` parameter and the page size | medium | mitigate | `PAGE_SIZE` remains a server-side constant of 6 and is never accepted from the request; `SearchResults` derives `pageCount` from that same constant rather than from a prop; `validateSearchParams` rejects a page outside 1..`MAX_PAGE` with a 400, so a very large offset can never be requested |
| T-03-14 | Tampering | Double-submitted page navigation | low | mitigate | Every pagination control carries `disabled` while a fetch is in flight, so two overlapping page requests cannot be issued from the UI; the server is idempotent for reads regardless |
| T-03-15 | Information Disclosure | Deep-page enumeration of the doctor catalog | low | accept | The catalog is deliberately public reference data restricted by RLS to active doctors; paging through it exposes exactly what a single unfiltered search already exposes, and no private field is present in the response |
| T-03-SC | Tampering | npm/pip/cargo installs | high | accept | This phase installs zero packages (03-RESEARCH.md: "No external packages are introduced by this phase"), so the legitimacy gate has nothing to audit; re-arm if any plan later adds a dependency |

## Planner assumptions (flagged, not dismissed)

- **Offset pagination is a locked decision, not a recommendation.** The project's own `supabase-postgres-best-practices` skill prefers cursor/keyset pagination for deep-paginated datasets. D-11 and D-15 lock classic numbered `.range()` pagination, and the production dataset is roughly a dozen demo doctors, so the OFFSET tradeoff is immaterial here. Recorded, not overridden.
- **Discoverability of `/search` is out of scope.** No requirement, decision, or task in `TASKS.md` asks for a navigation entry point to `/search` from the home page or the site header, and `components/site-header.tsx` renders nothing for an anonymous visitor. `/search` and `/doctors/[id]` are reachable by direct URL only in this phase. Flagged so a later phase (or a pre-defence polish pass) can decide deliberately rather than discovering it during a demo.
