<objective>
Give the doctor the cancellation action the patient already has, on the appointment list plan 05-03 built, through the route plan 05-02 built. This is the last capability of the phase and deliberately the smallest: no new endpoint, no new function, no new copy — the same operation reached by the second legitimate actor, with the acting party decided inside the database from `auth.uid()` rather than by anything the client says.

Purpose: D-12 makes cancellation one operation with two actors, and the cheapest way to get that wrong is to build a second doctor-flavoured endpoint that drifts — different rejection copy, a different slot-release path, or worst of all a client-supplied "who cancelled" field. Wiring the doctor into the existing route and proving both parties see the identical account of the same cancelled appointment is what keeps the two paths one path.

Output: the cancellation dialog and destructive row action on `/doctor/appointments`, and the doctor-side cases added to `tests/e2e/appointment-cancel.spec.ts` alongside the patient cases plan 05-02 wrote.

Scope guard: no new route, no migration, no change to `cancel_appointment()`. No reschedule control is added to the doctor page (D-06, D-07). No attendance-outcome control of any kind is added (D-16).

Flagged assumption (spec-less probe, §A): APPT-06 returned `unclassified` from the deterministic edge probe. Its edges are resolved by human-authored decisions — who may cancel and until when by D-12, the resulting status by D-14, the slot release by D-15, and the confirmation-dialog contract by D-13 — and by the UI-SPEC statement that the cancellation trigger appears "on any appointment row, patient or doctor view". Nothing about APPT-06 is left to inference beyond the copy discretion D-13 already grants.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| doctor browser -> `PATCH /api/appointments/[id]/cancel` | Untrusted input crosses here: an appointment id in the path, an optional free-text reason, and any extra keys the client chooses to add |
| route handler -> `cancel_appointment()` | The handler performs no ownership check of its own; the function body is the boundary for both actors alike |
| `SECURITY DEFINER` function body -> `appointments`, `availability_slots`, `notifications` | RLS is bypassed inside the function, so its `patient_id = auth.uid() or doctors.profile_id = auth.uid()` filter is the sole authorization control |
| doctor session -> another doctor's appointment rows | Ownership boundary; crossing it must be indistinguishable from targeting a nonexistent row |
