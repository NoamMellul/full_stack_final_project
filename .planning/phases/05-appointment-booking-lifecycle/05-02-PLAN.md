<objective>
Give both the patient-facing UI and the API the ability to cancel an upcoming appointment, and make the freed slot genuinely bookable again. This is the first expansion outward from plan 05-01's proven booking slice: the same guard-validate-RPC-translate route shape, the same dialog-then-refresh page shape, now applied to the `cancel_appointment()` function that plan 05-01 already deployed.

Purpose: cancellation is the half of the lifecycle that decides whether the platform loses inventory. An appointment that cancels but leaves its slot marked `booked` silently removes that time from every future search — the failure is invisible to the person who caused it and permanent until someone notices. Wiring the release inside the same transaction as the status change, and proving with a real re-booking that the freed slot is claimable again, is what closes APPT-07 rather than asserting it.

Output: `PATCH /api/appointments/[id]/cancel`, the cancellation confirmation dialog and destructive row action on `/patient/appointments`, and `tests/e2e/appointment-cancel.spec.ts` covering patient cancellation, slot release, re-booking, ownership scoping and the rejection paths.

Scope guard: the doctor-side cancellation action lives on `/doctor/appointments` and is plan 05-05; this plan builds the route both actors share and exercises it from the patient side only. Reschedule is plan 05-04. Nothing here writes an attendance outcome to `appointments.status` (D-16).

Flagged assumption (spec-less probe, §A): APPT-05 and APPT-07 both returned `unclassified` from the deterministic edge probe. Their edges are resolved by human-authored decisions — who may cancel and until when by D-12, the status values by D-14, the slot release by D-15 — with one genuinely open reading carried explicitly: D-15 conditions the slot release on the slot still being in the future, but D-12 already makes a cancellable appointment one whose `start_at` has not passed, so the `start_at > now()` predicate on the release `update` is unreachable in normal operation. It is kept anyway as a cheap guard against a future caller that relaxes D-12, and is called out here rather than silently dropped. This reading should be confirmed at end-of-phase verification.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `PATCH /api/appointments/[id]/cancel` | Untrusted input crosses here: an appointment id in the path and an optional free-text reason in the body |
| route handler -> `cancel_appointment()` | The handler performs no authorization of its own beyond a session check; the function body is the boundary |
| `SECURITY DEFINER` function body -> `appointments`, `availability_slots`, `notifications` | RLS is bypassed inside the function, so its own `patient_id = auth.uid() or doctors.profile_id = auth.uid()` filter is the sole authorization control |
| patient session -> another patient's appointment rows | Ownership boundary; crossing it must be indistinguishable from targeting a nonexistent row |
