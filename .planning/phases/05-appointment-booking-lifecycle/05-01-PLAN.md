<objective>
Deploy the three transactional Postgres functions this whole phase is built on, then prove the entire booking path end to end on the thinnest real slice: a logged-in patient opens a doctor's public profile, clicks a slot, confirms it in a dialog, and lands on their own appointments page seeing the booked appointment. Every layer the phase will later expand into — the `SECURITY DEFINER` RPC, the patient-role guard, manual validation, the REST route, the custom-SQLSTATE translation, the Asia/Jerusalem display helpers, the upcoming/past split, and the derived status badge — is wired for keeps on that single path.

Purpose: the platform's stated core value is a database-enforced guarantee that two patients never book the same slot. That guarantee lives in one conditional `UPDATE` statement inside `book_appointment()`. Proving it end to end on the first commit, under real `Promise.all` concurrency, means an architectural dead-end in the locking design is found once — before cancel, reschedule, and two history pages are layered on top of it.

Output: the appointment-functions migration applied to the remote database, `requirePatient()`, `lib/validation/appointments.ts`, `lib/appointments.ts`, `POST /api/appointments`, `GET /api/patient/appointments`, the `/patient/appointments` page, the enabled booking CTA plus confirmation dialog on `/doctors/[id]`, and the booking end-to-end spec.

Scope guard: this plan writes the cancel and reschedule functions into the migration (one migration, one push, per RESEARCH's primary recommendation) but wires no cancel or reschedule route, UI, or spec — those are plans 05-02, 05-04 and 05-05. This plan never writes `appointments.status` values other than `scheduled`, and never adds a status-transition job of any kind (D-16).

Flagged assumption (spec-less probe, §A): every APPT requirement returned `unclassified` from the deterministic edge probe, because they are behavioural/workflow requirements rather than data-shape ones. For this plan's six requirements the edges are resolved by human-authored decisions rather than left open — APPT-01 by D-01/D-02/D-03/D-05/D-19, APPT-02 by D-11 and RESEARCH's locking strategy, APPT-03 and APPT-04 by the single conditional `UPDATE`, and APPT-10/APPT-11 by D-17/D-18 plus the UI-SPEC Layout section. One genuinely open reading is carried explicitly: the badge on an upcoming appointment reads `Confirmed` (UI-SPEC) while the stored status is `scheduled` (RESEARCH). That divergence is deliberate and is asserted as a truth above so it cannot be "fixed" by writing `confirmed` into the database.
</objective>

  <name>Task 1: Decide how far to close the direct-insert bypass on `appointments`</name>
  <decision>Whether the migration in Task 2 also removes the `authenticated` role's direct `INSERT` privilege on `public.appointments`, forcing every appointment row through `book_appointment()`.</decision>
  <context>
    The Phase 1 RLS policy `appointments_insert_patient` (`for insert with check (patient_id = auth.uid())`) lets any authenticated patient POST an `appointments` row straight through PostgREST without ever calling `book_appointment()`. RESEARCH.md Pitfall 1 works this through: the `appointments_active_slot_unique_idx` partial unique index still prevents a genuine double booking on that path, so APPT-02 holds either way. What the bypass path does break is APPT-04 — a direct insert never touches `availability_slots.status`, so the slot stays `available` and keeps appearing as bookable in search and on the profile page while an active appointment already points at it.

    This is asked before Task 2 because a grant change on the shared remote database is one-way in practice: undoing it needs another migration, and any code written afterwards assumes the privilege model it establishes. A grep of the repository confirms no application code inserts into `appointments` through the session-bound (`authenticated`) client — the only writers are `tests/e2e/helpers/appointments.ts` and `tests/e2e/admin-oversight-views.spec.ts`, both of which use the service-role client and are unaffected by a role grant.

    RESEARCH.md's own recommendation is to close it (Assumption A3, risk rated low either way).
  </context>
  <options>
    <option id="option-a">
      <name>Accept the residual gap — no grant change</name>
      <pros>Smallest migration; nothing about the Phase 1 privilege model changes; matches the trust model already used elsewhere in this codebase, where an RLS-permitted path is simply never invoked by first-party code.</pros>
      <cons>APPT-04's "booking marks the slot unavailable immediately" guarantee is only true for callers who go through the route; a hand-crafted PostgREST insert leaves `availability_slots.status` desynchronised from `appointments`, and nothing in the database detects it.</cons>
    </option>
    <option id="option-b">
      <name>Revoke `insert` on `public.appointments` from `anon` and `authenticated` in the same migration</name>
      <pros>Closes the gap completely: `book_appointment()` runs as its definer and is unaffected, the service-role test fixtures are unaffected, and every appointment row is therefore guaranteed to have flipped its slot atomically.       <cons>Leaves `appointments_insert_patient` in place as a policy that can no longer be exercised, which needs a comment in the migration to avoid confusing a later reader; any future feature that wants a direct patient insert has to add a function or restore the grant.</cons>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `/api/appointments` and `/api/patient/appointments` | Untrusted JSON crosses here: a slot id and any extra keys the client chooses to send, including a forged `patientId` |
| route handler -> Postgres via the session-bound Supabase client | RLS (`appointments_select_own_or_admin`) evaluates here for reads; for writes this boundary is crossed by an RPC call |
| `SECURITY DEFINER` function body -> the rest of the database | RLS is bypassed entirely inside the function, so the function body is the sole authorization boundary for every write it performs |
| patient session -> another patient's `appointments` rows, and -> a doctor's `availability_slots` rows | Ownership boundary: a patient legitimately flips a doctor-owned slot, but only through the one narrow validated path |
